2-A) **효율적 호출 — 3가지 분할 전략 (사용자 직언)**.

   가) **Thinking budget 제어** (gemini-2.5-flash 의 thinking 토큰 절약)
       - 테스트에서 단순 prompt 한 호출에 thinking=227 / output=67 — thinking 이 답보다 3배.
       - generationConfig 에 `thinkingConfig.thinkingBudget` 명시:
         * simple_intent (인사·날짜·tool 라우팅) → thinkingBudget=0 (thinking 끔)
         * normal (list 조회·필터 적용) → thinkingBudget=128
         * complex (multi-step 분석·요약) → thinkingBudget=512
         * deep (장문 추론) → thinkingBudget=2048
       - intent 분류는 사용자 메시지 길이 + 키워드 + tool 호출 깊이로 자동 판정 (휴리스틱 함수).
       - thinking 끄면 응답 속도 2~3배 빠름 + 비용 50% 이상 절감.

   나) **Max tokens 적응** (응답 형식 별 limit 분기)
       - 응답 형식별 max_output_tokens:
         * single fact / yes-no → 50
         * tool call JSON → 200
         * list (10 row) → 600
         * 카드 요약 → 800
         * 자유 응답 / 분석 → 1500
       - 호출 전 prompt 분석으로 형식 추정 → 적정 limit 설정. 토큰 낭비 방지.

   다) **Planner pattern — 큰 task 를 sub-task 로 분할**
       - 사용자 메시지가 multi-step (예: "PROD-A 의 모든 lot 인폼 받고 모듈별로 정리하고 메일 발송") 이면:
         a. 1차 호출 (cheap, planner): "이 task 를 sub-task 로 분할해" → 단계 list 받기 (max 100 tokens, thinking 0)
         b. 각 sub-task 별 호출 (tool calling, 분리 호출 — 짧고 정확)
         c. 마지막 호출 (synthesizer): 모든 sub-task 결과 합쳐 자연어 요약 (500 tokens)
       - 단계 수 별 비용 절감: 1회 거대 호출 (5000 tokens, thinking 2000) → planner 분할 (100+200×N+500 ~ 1500 tokens 평균). 30~50% 절감.
       - planner 는 thread context (task #18) 의 entities 활용 — 같은 정보 중복 호출 X.
       - 단계 결과 캐시 — 같은 sub-task 재호출 시 cache hit (thread 안 5분 TTL).

   라) 호출 metrics 기록
      - 각 호출에 {intent, complexity, thinking_budget, max_tokens, actual_tokens, cost_estimate, dt_s} 기록 → llm_usage.jsonl.
