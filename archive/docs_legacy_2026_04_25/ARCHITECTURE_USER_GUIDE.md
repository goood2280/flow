# flow 아키텍처 이해 가이드

이 문서는 개발자가 아닌 사람도 `flow`의 구조와 앞으로의 방향을 이해할 수 있도록 정리한 설명서다.

---

## 1. 이 앱은 어떤 앱인가

`flow`는 반도체 공정관리 전반을 한곳에서 다루기 위한 운영형 웹 앱이다.

쉽게 말하면 아래 일을 한 시스템 안에서 이어서 처리하려는 것이다.

- 공정 데이터 보기
- plan 대비 actual 추적
- 이슈 관리
- 회의 및 액션아이템 관리
- 변경점 기록
- 관리자 권한과 운영 설정 관리

즉 단순 대시보드가 아니라, 현업 엔지니어가 매일 쓰는 업무 도구에 가깝다.

---

## 2. 지금 쓰고 있는 기본 스택

### FastAPI

백엔드 웹 프레임워크다.

- 브라우저에서 오는 요청을 받는다.
- 로그인, 데이터 조회, 저장 같은 API를 만든다.
- Python 기반이라 데이터 처리 코드와 연결하기 쉽다.

### React

프론트엔드 UI 라이브러리다.

- 브라우저 화면을 구성한다.
- 페이지 이동 없이 빠르게 화면을 바꾼다.
- 복잡한 입력 폼과 대시보드 UI를 만들기 좋다.

### Polars

대용량 테이블 데이터를 빠르게 다루는 데이터 처리 라이브러리다.

- parquet, CSV 같은 파일을 읽는다.
- 필터, 집계, 컬럼 계산을 빠르게 수행한다.
- pandas보다 메모리와 속도 면에서 유리한 경우가 많다.

### Parquet / CSV

파일 기반 데이터 저장 포맷이다.

- 공정 데이터는 양이 많아서 보통 DB보다 파일 레이크 방식이 효율적일 때가 많다.
- 분석성 데이터는 파일로 다루는 편이 실무에서 흔하다.

### Postgres

관계형 데이터베이스다.

- 이슈, 회의, 메시지, 권한처럼 “사람이 같이 수정하는 운영 데이터”를 저장하는 데 강하다.
- 동시 수정, 검색, 정렬, 트랜잭션, 감사 추적에 유리하다.
- 현업 서비스에서 가장 많이 쓰는 운영 DB 중 하나다.

지금 `flow`는 운영 데이터까지 파일(JSON/CSV)로 많이 들고 있는데, 장기적으로는 운영 데이터 일부를 Postgres 같은 DB로 옮기는 것이 맞다.

---

## 3. 스캐폴딩이란 무엇인가

`스캐폴딩(scaffolding)`은 말 그대로 “골격”이다.

완성된 기능이 아니라, 앞으로 기능을 안전하게 쌓아 올릴 수 있도록 먼저 만들어 두는 구조를 뜻한다.

예를 들면 아래가 스캐폴딩이다.

- 폴더 구조를 먼저 나눈다
- 공통 저장 클래스(JsonFileStore)를 만든다
- Service / Repository / Domain 파일을 먼저 만든다
- 아직 모든 화면이 연결되지 않아도 구조만 먼저 준비한다

즉 스캐폴딩은 “지금 당장 다 쓰지는 않지만, 나중에 코드가 커져도 무너지지 않게 하는 골조”다.

---

## 4. 왜 층(layer)을 나누는가

작은 프로젝트는 한 파일에 다 넣어도 처음에는 빨리 돌아간다.
하지만 현업에서는 시간이 지나면 아래 문제가 거의 반드시 생긴다.

- 기능 수정 하나가 다른 기능을 깨뜨린다
- 버그 원인을 찾기 어렵다
- 파일 저장 방식이 제각각이라 장애가 난다
- 권한 체크가 여러 군데에 흩어진다
- 새 기능을 넣을 때 어디를 고쳐야 하는지 불분명하다

그래서 실무에서는 보통 역할별로 층을 나눈다.

### Router

HTTP 요청과 응답을 담당한다.

예:

- `/api/tracker/create` 요청을 받는다
- 요청값을 읽는다
- Service를 호출한다
- 결과를 JSON으로 돌려준다

Router는 “입구” 역할만 해야 한다.

### Service

실제 업무 흐름을 담당한다.

예:

- 이슈 제목이 비어 있으면 막는다
- 상태 변경 시 revision을 올린다
- 작성자/수정자 정보를 넣는다
- 필요한 Repository를 순서대로 호출한다

Service는 “무슨 일을 어떤 순서로 처리할지”를 담당한다.

### Repository

저장소 접근만 담당한다.

예:

- JSON 파일 읽기
- DB에 저장
- parquet 파일 조회
- 메시지 목록 불러오기

Repository는 “어디에 어떻게 저장할지”를 담당한다.

### Domain

업무 개념 자체를 정의한다.

예:

- 이슈는 어떤 필드를 가져야 하는가
- 회의록은 어떤 상태를 가져야 하는가
- lot watch는 어떤 규칙으로 판단하는가

Domain은 “이 비즈니스가 무엇인가”를 표현한다.

## 5. 현업에서는 어떻게 정의하고 움직이는가

실제 현업에서는 대체로 아래처럼 생각한다.

### 운영 데이터와 분석 데이터는 분리한다

- 운영 데이터:
  이슈, 회의, 액션아이템, 메시지, 권한, 알림
- 분석 데이터:
  parquet, csv, ML feature, 대용량 측정값

이 둘은 성격이 다르다.

운영 데이터는 정확하고 안전하게 저장되어야 한다.
분석 데이터는 크고 빠르게 읽히는 것이 중요하다.

그래서 보통 운영 데이터는 Postgres 같은 DB에, 분석 데이터는 파일 레이크나 S3에 둔다.

### API 서버는 얇게 유지한다

라우터에 모든 로직을 몰아넣지 않는다.

그 이유는 아래와 같다.

- 테스트하기 쉽다
- 다른 화면에서도 같은 로직을 재사용할 수 있다
- 저장 방식을 JSON에서 Postgres로 바꿔도 영향 범위가 줄어든다

### 저장은 공통 방식으로 처리한다

현업에서는 파일 저장을 해도 보통 아래를 통일한다.

- atomic write
- revision
- updated_at
- updated_by
- audit log

이게 없으면 누가 언제 무엇을 바꿨는지 추적하기 어려워진다.

### 백그라운드 작업은 상태를 보여준다

차트 계산, 백업, 스케줄러는 돌기만 하면 끝이 아니다.

운영에서는 꼭 아래를 본다.

- 마지막 실행 시각
- 성공/실패 여부
- 마지막 에러
- 다음 실행 예정

이 정보가 없으면 “왜 화면이 비었는지” 알 수 없다.

## 6. 현재 `flow`의 좋은 점

- 이미 도메인 기능이 잘 잡혀 있다
- 반도체 공정 운영에 필요한 화면 구성이 명확하다
- FastAPI + React + Polars 조합이 목적에 잘 맞는다
- 데이터 레이크 기반 분석형 기능과 운영형 기능이 한 제품으로 묶여 있다

즉 방향 자체는 좋다. 문제는 “기능이 부족하다”보다 “구조를 더 오래 버티게 다듬어야 한다”에 가깝다.

---

## 7. 지금 구조에서 실제 운영 중 생길 수 있는 문제

### 1. 파일 동시 수정 충돌

여러 사용자가 같은 JSON 파일을 거의 동시에 저장하면 마지막 저장이 덮어쓸 수 있다.

### 2. 데이터 루트 오설정

로컬 경로, 운영 경로, 예전 경로가 섞이면 화면은 뜨는데 일부 차트만 깨질 수 있다.

### 3. 라우터 파일 비대화

한 라우터 안에 권한 체크, 데이터 처리, 저장, 알림 로직이 다 들어가면 수정이 위험해진다.

### 4. 운영 데이터 추적 부족

이슈나 회의 내용이 바뀌었을 때 누가 바꿨는지, 언제 바꿨는지, 이전 버전이 무엇인지 관리가 약해진다.

### 5. 백그라운드 작업 경합

차트 스케줄러, 백업, tracker poller가 한 프로세스에서 동시에 돌면 I/O가 겹칠 수 있다.

---

## 8. 그래서 앞으로 어떤 방향으로 가는가

핵심 방향은 아래 다섯 가지다.

### 1. 기존 코드를 한 번에 갈아엎지 않는다

지금 돌아가는 앱을 살려 둔 상태에서 점진적으로 옮긴다.

### 2. 새 구조를 병행 추가한다

`backend/app_v2` 같은 새 레이어를 두고, 기능별로 옮긴다.

### 3. 운영 데이터는 점차 DB 친화적으로 바꾼다

처음에는 JSON 저장을 유지하더라도, 구조는 나중에 Postgres로 옮기기 쉽게 만든다.

### 4. Tracker부터 시작한다

이유는 다음과 같다.

- 운영형 데이터라 구조 분리 효과가 크다
- create/update/comment 같은 행위가 분명하다
- revision, updated_by, 상태 변경 알림 같은 실무 요구가 많다

### 5. 문서와 구조를 같이 남긴다

혼자 개발할 때도 문서가 있어야 나중에 왜 그렇게 만들었는지 잊지 않는다.

## 8-1. 운영 배포는 어떻게 하는가

실제 운영에서는 코드와 데이터가 분리되어야 한다.

예를 들면 아래처럼 나누는 방식이 좋다.

- 코드 배포 폴더:
  `/config/work/holfast-api`
- 운영 데이터/로그/설정 폴더:
  `/config/work/sharedworkspace`

그리고 그 아래를 다시 나눈다.

- 앱 상태, 사용자 데이터, 회의/이슈/메시지, 설정:
  `/config/work/sharedworkspace/holweb-data`
- 공정 원천 데이터:
  `/config/work/sharedworkspace/DB`
- Base 룰북/보조 데이터:
  `/config/work/sharedworkspace/Base`

이렇게 나누는 이유는 단순하다.

- 앱 코드는 재설치하거나 업데이트할 수 있다
- 하지만 운영 데이터는 절대 같이 날아가면 안 된다

그래서 `setup.py`는 코드만 갱신하고, 운영 데이터는 sharedworkspace 아래에 남겨 두는 방식이 현업에서 훨씬 안전하다.

## 9. 추천하는 최종 그림

### 프론트

- pages: 화면 조립
- features: 기능 단위 UI와 API 호출
- shared: 공통 컴포넌트와 공통 훅

### 백엔드

- routers: 요청/응답
- services: 업무 흐름
- repositories: 저장소 접근
- domain: 업무 규칙

### 데이터

- 운영 데이터: Postgres 또는 SQLite
- 분석 데이터: parquet / CSV / S3

## 10. 한 줄로 정리

`flow`는 이미 제품 방향은 맞다.
앞으로 해야 할 일은 기능을 새로 만드는 것보다, 지금 있는 기능을 “실제 운영을 버티는 구조”로 재정렬하는 것이다.

그 첫 단계가 바로 `tracker -> service/repository/domain 분리`다.

---

## 11. 테스트 데이터와 실데이터가 다를 때

이것도 실제로 아주 중요한 문제다.

현업에서는 테스트할 때 만든 데이터와 사내 실데이터가 아래처럼 다를 수 있다.

- 경로가 다르다
- 파일명이 다르다
- 컬럼명이 다르다
- 대문자/소문자가 다르다
- 데이터 포맷이 wide/long으로 다르다

이럴 때 앱이 너무 딱딱하면 바로 깨진다.

그래서 좋은 운영 앱은 아래처럼 동작해야 한다.

- 내부에서는 표준 이름을 정해 둔다
- 외부 데이터는 alias와 adapter로 맞춘다
- 경로는 운영 중에도 바꿀 수 있다
- 못 찾으면 에러만 내지 말고 후보와 진단 메시지를 보여준다

즉, 현실적인 앱은 “정확히 일치해야만 동작하는 앱”이 아니라 “차이를 흡수하면서도 내부 일관성을 유지하는 앱”이어야 한다.
