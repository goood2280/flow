# Flow 개선 계획 (PLAN)

개선·최적화 요청을 받은 코드 에이전트(사내 VM 의 OpenCode·Gemma4 포함)가 **무엇을, 어떤 순서로, 현장 조건에 맞춰 어떻게
조절해 구현할지** 정하는 문서다. 먼저 `AGENTS.md`(규칙) → `README.md`(운영) → `docs/ARCHITECTURE.md`(동작 구조)를 읽고 온다.

## 이 문서 쓰는 법

1. 아래 **항목 목록**에서 요청과 맞는 항목을 고른다. 상태가 `계획`인 항목만 구현 대상이다.
2. 그 항목의 **사내 조건 확인** 표를 먼저 채운다(명령·로그·설정으로 확인하고, 모르면 사용자에게 묻는다). 조건 결과가 어떤
   단계를 할지·건너뛸지·기본값을 얼마로 둘지를 정한다.
3. **단계(Phase)** 를 순서대로 진행한다. 각 단계는 독립 배포 가능하고, 환경변수 하나로 끌 수 있어야 한다(기본값은 꺼짐 또는
   기존 동작과 같음). 단계를 마칠 때마다 완료 조건의 숫자를 사용자에게 보고하고 다음 단계 진행을 확인받는다.
4. 구현이 끝나면 이 문서의 상태·결정 기록을 갱신하고, 동작이 바뀌면 `ARCHITECTURE.md`·README 해당 절도 고친다.

규칙: 목표 수치를 실측처럼 쓰지 않는다. 사내 코드·질문·로그를 외부 서비스로 보내지 않는다. 평가 결과에는 질문 원문 대신
건수·비율만 남긴다(공개 저장소).

## P3. VM 고정 자원 예산·최초 설치 실패 진단 (2026-10-02)

사용자 요청 범위의 기존 동작 수정이다. 스케줄러 통합 P2의 다음 단계나 추가 병렬 작업 도입은 포함하지 않는다.

### 사내 조건 확인

| 조건 | 확인 결과·근거 |
|---|---|
| 작업 위치 | GitHub flow 원격이 있는 개발 체크아웃. 기존 미커밋 변경을 보존하고 번들을 재빌드한다 |
| VM 크기·현재 설정 | 문서상 8코어/128GiB. 실제 VM에는 접근하지 못하므로 auto/large 합성 호스트 테스트로 계산식을 확인한다 |
| 현재 계산 예산 | 8코어/128GiB auto·large의 공용 CPU·Polars 예산은 8코어, 캐시 풀은 61.44GiB. root/product RAM 예열은 폐기되어 옛 2코어 기준은 활성 병목이 아님 |
| 의도한 운영 제한 | CPU 환경변수·관리자 캐시 예산을 임의 삭제하지 않는다. 기동 로그와 `flow_ctl.bat perf`에서 제한 위치와 값을 진단한다 |
| 사내 pip/npm 저장소 | 직접 접속 불가. 사용자는 오류를 지금 확인할 수 없으며 최초 설치 때 미설치 패키지 출력을 요청했다 |
| 설치 결함 | 기본 전체 설치가 필수 패키지 FAIL을 성공으로 끝낼 수 있음. 여러 패키지를 묶은 설치는 하나만 mirror에 없어도 전체 실패 가능. strict에서 검증된 dist도 npm 재설치 시도 |

### 한 단계 수정과 검증

- 현재 공용 CPU 예산을 합성 호스트와 실제 요청 가드로 검증한다. large를 제한하는 small 강제값·CPU 보호 기준·활성 캐시 예산은 적용 위치와 함께 진단한다. 폐기된 예열은 변경하지 않는다.
- 설치 목록과 점검 목록을 일치시키고, 묶음 설치 실패 후 필요한 패키지를 개별 확인·재시도한다. 최종 콘솔 표와 JSON에 누락·버전 부족·import 실패를 기록하고 필수 실패는 종료 코드에 반영한다.
- 소스·lock 지문과 배포 파일이 맞는 번들은 strict에서도 npm 없이 사용한다. 필요한 재빌드는 lock 기준으로 실행한다.
- 검증: 격리 root의 관련 pytest, 빈 설치 폴더·패키지 저장소 없는 환경의 실패 진단, frontend 검사·번들 재빌드. 운영 VM의 실제 패키지 가용성과 혼합 부하 성능은 미측정이다.
- 회귀 검증 결과: 격리 root의 관련 pytest **59개 통과**, frontend 디자인·구조 검사와 production 빌드 통과. 빈 venv에서 패키지 저장소를 막으면 필수 10개 누락을 출력하고 exit 1, 의존성이 갖춰진 환경은 exit 0이다. strict에서도 검증된 화면은 npm을 생략하며, 추출본 `/health`·`/`·`/version.json`과 주요 라우터를 확인했다. 프런트 빌드에는 기존 JSX 중복 속성·buffer 외부화·큰 chunk 경고가 남는다.

## P1. 홈 에이전트 작업 선택 — 선택지 + 확신도 (Jev 방식)

### 결정 기록

- 2026-10-01: 같은 설계의 1차 구현(`core/flowi_intent.py`: 학습 예시로 LLM 건너뛰기 + 되묻기 버튼)을 만들었다가 **사용자 결정으로
  전부 제거**했다. 현재 운영은 기존 흐름(규칙 → 계획 LLM → 한 줄 되묻기)이다. 다시 도입할 때는 이 계획의 단계와 조건 확인을
  거쳐 **기능 플래그 기본 꺼짐**으로 넣고, 켤지는 사용자가 정한다.
- 남아 있는 관련 변경: 계획 LLM 프롬프트 키 순서(고정 내용 앞, `request` 맨 뒤 — 서버 prefix cache 재사용).
  `tests/test_planner_prompt_order.py`.

### 배경: Jev 방식이란

- Jev(TypeSafe)는 글을 생성하지 않고 **주어진 선택지 중 하나와 확률(확신도)**만 돌려주는 결정 모델이다. REFLEX 구조는
  확신도가 기준 이상이면 그 선택을 바로 실행하고, 낮으면 큰 LLM 에 넘긴다.
- 공개 평가에서 "어떤 도구를 부를지"는 매우 정확했지만(98%대), "도구를 부를지 말지"는 절반 수준이었다. 저자들도 일반 라우팅은
  이미 정확해 개선 여지가 작을 수 있다고 적었다. → **이득은 속도·비용과 '애매할 때 사람에게 고르게 하기'에 있다.** 호출 여부·권한
  판단은 코드 규칙이 계속 맡는다.
- Jev 자체는 사외 호스팅 API 라 **쓰지 않는다**(사내 내용 외부 전송 금지). 같은 구조를 로컬 규칙·경량 점수·사내 Gemma4 로 만든다.

참고: [REFLEX with Jev (arXiv)](https://arxiv.org/html/2609.26532),
[Jev for AI agents (Refix)](https://www.refix.ai/news/jev-for-ai-agents/)

### 현재 흐름과 적용 지점

`ARCHITECTURE.md` 7절의 순서도가 정본이다. 적용할 수 있는 자리는 세 곳이다.

| 자리 | 지금 | 문제 | Jev 방식으로 바꿀 점 |
|---|---|---|---|
| A. 규칙 처리기 연쇄 (`data_chat.execute`) | 고정 순서, 먼저 잡는 쪽이 처리 | 확신도·경합 개념이 없어, 두 처리기가 모두 맞는 질문은 순서 때문에 조용히 엇갈린다(순서 의존 패치가 누적) | 처리기가 "잡을 수 있다 + 점수"를 내고, 1위가 확실할 때만 실행, 비슷하면 선택지 |
| B. 계획 LLM (`data_chat._feature_plan`) | 규칙이 못 잡으면 1~2만 자 프롬프트로 `{action, params}` 전체를 생성 | 느릴 수 있다(Gemma4 호출 제한시간을 최소 60초로 둘 정도), 파라미터까지 생성 | 작업 **선택만** 싸게 하고(로컬 점수 또는 선택 전용 호출), 파라미터는 기존 규칙 추출기가 채움 |
| C. 되묻기 (`action == "clarify"`) | "제품명과 조회 조건을 알려 주세요" 한 줄 | 무엇을 다시 써야 할지 모른다 | 가능성 높은 작업 2~3개를 버튼으로. 화면은 이미 `tool.clarification.options` 를 그린다 |

### 사내 조건 확인 (먼저 채운다)

| # | 확인할 것 | 확인 방법 | 결과에 따른 조절 |
|---|---|---|---|
| 1 | 계획 LLM 이 얼마나 자주·얼마나 오래 불리나 | 대화 sqlite 의 `routing_trace.events` 에서 `llm_planner` 비율, `elapsed_ms` 분포 | 비율이 낮거나(예: 10% 미만) 호출이 수 초 이내면 Phase 2·3 의 이득이 작다 → Phase 1 만 |
| 2 | 잘못 처리된 질문이 있나 | 👎·교정(`home_feedback.sqlite3`), 관리자 질문 해석 규칙 수, 운영자 인터뷰 | 오처리가 규칙 연쇄에서 나오면 Phase 4 검토, 계획 LLM 에서 나오면 Phase 3 |
| 3 | 학습 예시가 충분한가 | 성공 질문(`chat_sample_prompts.json` `successful`)의 작업별 건수, 관리자 규칙 수 | 작업별 수 건 미만이면 Phase 2 는 관리자 규칙만 근거로 하거나 보류 |
| 4 | 사용자 수·공유 정책 | 활성 사용자 수, 사용자 결정 | 다른 사용자의 질문을 근거로 쓸지(기본: 서로 다른 3명 이상 합의만), 개인 것만 쓸지 |
| 5 | 게이트웨이가 확률(logprobs)을 주나 | 아래 **게이트웨이 확인** 스크립트 | 준다 → Phase 3 에서 확률을 확신도로. 안 준다 → enum 제한 선택 + 자기평가 없이 Phase 1·2 로 보완 |
| 6 | 게이트웨이가 선택 제한을 지원하나 | `llm_adapter` 의 json_schema 지원 기록(`_capability_state(cfg, "json_schema")`), vLLM 이면 `guided_choice` | 지원 → 선택 전용 호출에서 선택지 밖 답이 원천 차단. 미지원 → 답을 목록과 대조해 벗어나면 기존 경로로 |
| 7 | prefix cache 가 켜져 있나 | 게이트웨이 운영자에게 확인(vLLM `enable_prefix_caching`), 같은 프롬프트 두 번 호출 지연 비교 | 꺼져 있으면 프롬프트 순서 효과가 없다 — 켜 달라고 요청하거나 선택 전용 호출을 짧게 |
| 8 | 되묻기 답을 학습에 써도 되나 | 사용자 결정(현재: 쓰지 않음) | 쓰지 않는 것이 기본. 허용되면 Phase 1 의 선택 결과를 예시로 기록(합의 규칙 동일 적용) |

게이트웨이 확인(설치 폴더, 격리 환경 아닌 운영 설정으로 1회만, 질문 원문 대신 합성 문장 사용):

```python
from core import llm_adapter
out = llm_adapter.complete("다음 중 하나를 번호로만 답하라: 1) 위치 2) 수율 3) 스플릿\n질문: 랏 지금 어디야",
                           request_overrides={"max_tokens": 1, "logprobs": True, "top_logprobs": 5})
print(out.get("ok"), out.get("text"))
print(((out.get("raw") or {}).get("choices") or [{}])[0].get("logprobs"))   # None 이면 확률 미지원
```

    ④ 관리자 질문 해석 규칙. 👎 받은 (질문, 작업)은 오답 예시로.
  - 동작: 각 질문을 `flowi_turn.execute` 로 재생하되 **LLM 은 모의**(호출되면 "LLM 필요"로 기록), 데이터 접근이 필요한 처리기는
    합성 root 로. `routing_trace.events` 에서 처리 주체(handler/rule_planner/llm_planner)와 결과 작업을 모은다.
  - 출력: 건수·비율만(원문 없음) — 규칙으로 처리된 비율, LLM 이 필요한 비율, 기대와 다른 작업 비율, **두 처리기 이상이 잡을 수
    있는 질문 비율**(각 처리기를 단독으로 돌려 확인), 되묻기 비율.
- 완료 조건: 기준선 숫자를 이 문서 결정 기록에 적는다. 이 숫자 없이 다음 단계로 가지 않는다.

#### Phase 1 — 되묻기를 선택지로 (가장 안전, 추천 첫 단계)

- 계획 LLM 이 `clarify` 를 돌려주거나 LLM 이 없을 때, 가능성 높은 작업 2~3개를 `tool.clarification` 으로 준다.
  - 형식: `{"kind": "intent", "title": "어떤 작업으로 처리할까요?", "options": [{"label", "value"}], "allow_other": true}`
  - `value` 는 **기존 규칙이 바로 잡는 문장**(원래 질문의 제품·랏 + 규칙 키워드, 예: `PRODA A1001 현재 위치 보여줘`).
    그래서 선택 뒤의 처리는 100% 기존 경로다.
  - 순위: 작업별 기본 예문(seed) + 관리자 규칙 + (조건 4 에 따라) 성공 질문과의 유사도. LLM 을 쓰지 않는다.
- 플래그: `FLOW_HOME_INTENT_OPTIONS=1` 일 때만(기본 꺼짐). 끄면 기존 한 줄.
- 완료 조건: 되묻기 뒤 사용자가 선택지를 누른 비율, 선택 뒤 완료 비율(평가셋 + 운영 로그). 되묻기 문구를 검사하는 기존 테스트 유지.

#### Phase 2 — 학습된 예시로 확신하면 계획 LLM 생략

- 위치: `_feature_plan` 에서 규칙 계획이 비고 계획 LLM 을 부르기 직전. 확신하면 그 작업을 고르고 **기존 규칙 파라미터 추출**
  (제품·랏·기간)을 그대로 탄다.
- 근거는 학습 예시만: 관리자 규칙, 이 사용자의 성공 질문, 서로 다른 3명 이상이 같은 작업으로 성공한 질문(조건 4). 👎 받은 쌍 제외.
  seed 예문은 근거로 쓰지 않는다(없는 사실로 LLM 을 건너뛰게 된다).
- 점수(참고 구현): 질문을 정규화(제품→`{p}`, 랏→`{lot}`, 숫자→`0`, 소문자) → 글자 2·3-gram TF-IDF → 예시와 코사인 유사도 →
  작업별 최고점. **확신 = 1위 점수 ≥ 기준 그리고 1위−2위(다른 작업) ≥ 차이 기준.** 초기값 0.82 / 0.15, Phase 0 평가에서
  "확신한 것 중 정답 비율 ≥ 98%"가 되도록 현장에서 올린다.
- 사용자 식별: 라우터가 턴 동안 사용자 이름을 넘긴다(ContextVar). 예시 색인은 원천 파일 mtime 이 바뀔 때만 다시 만든다.
- 플래그: `FLOW_HOME_LOCAL_ROUTE=1`(기본 꺼짐), `FLOW_HOME_LOCAL_ROUTE_MIN_SCORE`, `…_MIN_MARGIN`.
- 기록: `flowi_routing.record("local_choice", action, score, margin, source)` — 응답의 `routing_trace.events` 에 남아 평가·진단에 쓴다.
- 완료 조건: 평가셋에서 확신 비율·확신 정밀도, 운영에서 계획 LLM 호출 감소율과 턴 지연(p50/p95) 변화.

#### Phase 3 — 선택 전용 LLM 호출 (조건 5·6 이 맞을 때)

- 계획 LLM 을 부르기 전에 **짧은 선택 전용 호출**을 먼저 한다: 도구 이름·한 줄 설명·번호 목록 + 질문, 출력은 번호 하나
  (`max_tokens` 1~2, 가능하면 `logprobs` 또는 `guided_choice`/json_schema enum).
- 확률이 기준 이상이면 그 작업 + 기존 규칙 파라미터 추출. 낮으면 기존 전체 계획 LLM(또는 Phase 1 선택지, 상위 2~3개를 순서로 사용).
- 확률을 못 받는 게이트웨이면: 선택 전용 호출을 enum 으로 제한하고, "모르겠다" 선택지를 반드시 넣어 그 답이면 기존 경로로.
- 턴당 LLM 호출 한도(6회)에 포함된다. 선택 전용 호출이 실패·시간 초과면 조용히 기존 경로.
- 플래그: `FLOW_HOME_CHOICE_CALL=1`(기본 꺼짐), `FLOW_HOME_CHOICE_MIN_PROB`.
- 완료 조건: 선택 전용 호출 지연(p50/p95)이 전체 계획 호출보다 확실히 짧은지, 평가셋 정확도가 떨어지지 않는지.

#### Phase 4 — 규칙 처리기 경합 해소 (Phase 0 에서 경합이 실제로 문제일 때만)

- 각 `dispatch(text, context, request)` 를 `claim(text, context) -> (점수, 이유)` 와 `run(...)` 으로 나눈다. 우선 경합이 잦은
  처리기 쌍부터(평가셋이 알려 준다), 한 번에 전부 바꾸지 않는다.
- 모든 claim 을 모아 1위가 확실하면 실행, 비슷하면 Phase 1 선택지. 동점은 **지금 순서**로 깬다(기존 동작 보존).
- 홈 챗 테스트 약 40개 파일이 회귀 기준이다. 변경 전후 실패 목록이 같아야 한다.
- 완료 조건: 평가셋의 경합 질문 오처리 감소, 기존 테스트 신규 실패 0.

### 배경 (착수 전 확인한 것)

- 필수 캐시 4종(lookup → pivot → WIP latest-lot → FAB 인덱스)은 이미 **자동 제품 순환 하나**가 제품 단위로 맡고 있었다
  (독립 FAB 인덱스·WIP 타이머는 은퇴). 문제는 "언제 다시 하나"였다.
- 순환은 매 바퀴 모든 제품의 4단계를 돌렸다. 단계마다 최신 검사가 있었지만 원천이 그대로여도 매번 도는 비용이 남았다:
  대시보드 최신 랏 파일을 **제품마다 전체 카탈로그로** 다시 쓰기(N 제품이면 한 바퀴에 N 번 + 행마다 파이썬 루프),
  WIP 캐시 신선도 확인 때 **JSON 전체 재파싱 + 전 항목 정렬·색인 재생성**(GIL 점유), FAB 서명 순회.
- WIP·FAB 매칭 캐시는 "30분 지남"이 기준이라 원천이 그대로여도 30분마다 FAB 전체를 다시 훑고, 반대로 원천이 바뀌어도
  30분이 안 됐으면 낡은 결과를 냈다. FAB 행이 없는 제품은 순환마다 WIP 전체 재스캔을 일으켰다.
